# Отладка

Ошибки, которые действительно возникли при подготовке сайта и пайплайна.
Для каждой: текст ошибки, гипотеза, способ проверки, решение.
Ошибки при запусках в GitHub Actions и на Helios дописываются в конце, в
разделе [Ошибки при запуске в CI](#ci).

## 1. `Permission denied` при запуске healthcheck { #e1 }

**Текст ошибки.**

```text
/bin/bash: line 17: scripts/healthcheck.sh: Permission denied
Exit code 126
```

**Гипотеза.** Код 126 означает «файл найден, но не исполняется». У скрипта нет
бита исполнения: его создали после команды `chmod +x scripts/*.sh`, которая
обработала только существовавшие на тот момент файлы.

**Проверка.** `ls -l scripts/` — у `healthcheck.sh` права `-rw-r--r--`, у
`helios.sh` — `-rwxr-xr-x`.

**Решение.** `chmod +x scripts/healthcheck.sh`. В CI ошибка проявилась бы так
же, если бит исполнения не попал в git. Git хранит его в режиме файла
(`100755`), и на Windows `chmod` его не выставляет. Отчёт по ЛР1 показывает,
что работа ведётся в Git Bash на Windows, поэтому там нужна команда
`git update-index --chmod=+x scripts/*.sh`. Проверка перед коммитом:
`git ls-files -s scripts/` — у всех `.sh` должен быть режим `100755`.

## 2. Ссылки на уравнения не превращаются в номера { #e2 }

**Текст ошибки.** Ошибки сборки нет. На скриншоте страницы с формулами вместо
«(1)» в тексте стоит исходный TeX: `Из \eqref{eq:ols} получаем прогноз…`.
Сами формулы при этом пронумерованы.

**Гипотеза.** MathJax настроен обрабатывать только элементы с классом
`arithmatex` (`ignoreHtmlClass: ".*|"`, `processHtmlClass: "arithmatex"`), а
`pymdownx.arithmatex` оборачивает в такой элемент только фрагменты внутри
`\(...\)`, `$$...$$` и окружения `\begin{…}`. Голый `\eqref{…}` в абзаце
остаётся обычным текстом.

**Проверка.** В собранном `site/report/math-check/index.html` строка
`\eqref{eq:ols}` стоит в `<p>` без обёртки
`<span class="arithmatex">`. Счётчик в замере: размеченных фрагментов 4,
ссылок среди них нет.

**Решение.** Писать ссылки внутри строчной формулы: `\(\eqref{eq:ols}\)`.
После исправления размеченных фрагментов стало 8 из 8, ссылки отображаются
как «(1)», «(2)» и ведут к формулам. Ослаблять фильтр MathJax до «обрабатывать
весь документ» не стали: тогда MathJax начал бы разбирать и блоки кода с `$`.

## 3. `check-yaml`: неизвестный тег `!ENV` { #e3 }

**Текст ошибки** (тот же безопасный загрузчик YAML, что в хуке pre-commit):

```text
mkdocs.yml -> ConstructorError: could not determine a constructor for the tag '!ENV'
  in "mkdocs.yml", line 10, column 11
```

**Гипотеза.** Хук `check-yaml` из `.pre-commit-config.yaml` разбирает YAML
безопасным загрузчиком, который не знает пользовательских тегов. `!ENV`,
которым `site_url` и метка сборки читаются из окружения, понимает только
загрузчик MkDocs.

**Проверка.** `yaml.safe_load` на `mkdocs.yml` падает с этой ошибкой, на
`mkdocs-cdn.yml` (без тегов) и `.github/workflows/site.yml` — проходит.

**Решение.** Хуку передан аргумент `--unsafe`: он проверяет только синтаксис
YAML, не создавая объектов, так что выполнения кода из файла не происходит.
Альтернатива — исключить `mkdocs.yml` из хука, но тогда синтаксические
ошибки в нём найдутся только при сборке.

## 4. Замер зависает, потому что страница так и не отрисовалась { #e4 }

**Текст ошибки.**

```text
playwright._impl._errors.Error: Page.evaluate: TypeError: Failed to execute
'getComputedStyle' on 'Window': parameter 1 is not of type 'Element'.
...
playwright._impl._errors.TimeoutError: Page.screenshot: Timeout 30000ms exceeded.
```

**Гипотеза.** В сценарии «CDN не отвечает» `document.body` ещё не существует.
Браузер не дошёл до `<body>`, потому что ждёт CSS шрифтов из `<head>`.
`page.screenshot` по умолчанию ждёт загрузки шрифтов, которая не наступит.

**Проверка.** `performance.getEntriesByName('first-contentful-paint')` пуст
через 48 с после начала загрузки; единственный незавершённый запрос — к
`fonts.googleapis.com`. При сразу отклонённом запросе к тому же адресу
первая отрисовка происходит через 0,21 с.

**Решение.** В скрипте замера отсутствие `body` и отрисовки обрабатывается как
результат, а не как сбой. Скриншот снимается, только если страница
отрисовалась, «зависшие» запросы перед закрытием браузера обрываются. Сама
ошибка оказалась главной находкой T4: внешний CSS в `<head>` при «висящем»
CDN даёт читателю пустой экран. Решение для сайта — `theme.font: false`.

## 5. Нет доступа к PyPI, npm и CDN в среде подготовки { #e5 }

**Текст ошибки.**

```text
$ uv add --group docs mkdocs mkdocs-material
  Caused by: Failed to fetch: `https://pypi.org/simple/pytest-cov/`
  Caused by: dns error
  Caused by: failed to lookup address information: Name or service not known

$ curl https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-svg.js
curl: (56) CONNECT tunnel failed, response 403
```

**Гипотеза.** Исходящий трафик идёт через прокси со списком разрешённых
адресов. PyPI, npm и CDN в него не входят, а GitHub входит (`git clone`
репозитория прошёл).

**Проверка.** Отчёт прокси о состоянии показал отказы `connect_rejected` для
`cdn.jsdelivr.net`, `fonts.googleapis.com`, `pypi.org`;
`git ls-remote https://github.com/actions/checkout` работает.
`uv add --offline` не помог: нужных пакетов не было в локальном кэше.

**Решение.**

- Версии пакетов сборки зафиксированы в `requirements-docs.txt` по уже
  установленному и проверенному набору (29 пакетов). `uv.lock` основного
  проекта не тронут.
- MathJax 3.2.2 взят из git-тега репозитория `mathjax/MathJax` (каталог
  `es5/` есть в опубликованных тегах) вместе с лицензией. SHA-256 файла
  `tex-svg.js`:
  `d4295dc33744836935c1399feece5159577b34c5c8ffb9f1c6324cd82e03a882`. Его можно
  сверить с файлом из npm-пакета `mathjax@3.2.2`.
- Отсутствие CDN использовано как стенд для T4: сайт проверен в сети, где CDN
  действительно недоступны.

## 6. Внешний запрос, которого не видит статическая проверка { #e6 }

**Текст ошибки.** `scripts/check_offline.py site` сообщает
`OK: 11 страниц, внешних подключений нет`. Замер в браузере на той же сборке:

```json
{"external_requests": 2, "external_hosts": ["api.github.com"], ...}
```

**Гипотеза.** Запрос делает не HTML, а JavaScript темы: при заданном
`repo_url` Material запрашивает у GitHub API число звёзд и форков для
виджета в шапке. Элемент виджета помечен атрибутом
`data-md-component="source"`.

**Проверка.** В шаблоне темы `partials/source.html` есть этот атрибут. После
его удаления в переопределении замер показывает
`"external_requests": 0`, а ссылка на репозиторий в шапке остаётся.

**Решение.** Переопределение `overrides/partials/source.html` без атрибута.
Вывод для проверки сайта: статическая проверка HTML нужна как быстрый барьер в
CI, но окончательный ответ даёт только браузер с журналом сетевых запросов.

## 7. Нестабильные якоря у заголовков на русском { #e7 }

**Текст ошибки.** Ссылка из P4 на раздел T4 о `known_hosts` была записана
по тексту заголовка. `mkdocs build --strict` на такие ссылки отвечает:

```text
WARNING -  Doc file 'report/setup.md' contains a link 'debugging.md#e5',
but the doc 'report/debugging.md' does not contain an anchor '#e5'.
Aborted with 3 warnings in strict mode!
```

**Гипотеза.** Расширение `toc` по умолчанию строит якорь из ASCII-символов
заголовка и отбрасывает кириллицу. Значит, у русских заголовков якоря либо
пустые и заменяются на `_1`, `_2`, либо состоят из случайно уцелевших
латинских слов.

**Проверка.**

```python
markdown.Markdown(extensions=["toc"]).convert(
    "## Как настроить `known_hosts`, не отключая проверку ключа хоста\n\n"
    "## Почему секреты недоступны\n\n## Отладка")
# <h2 id="known_hosts">…  <h2 id="_1">…  <h2 id="_2">…
```

Якорь `_1` зависит от порядка заголовков: вставка нового раздела выше сдвинет
все номера, и ссылки извне станут вести не туда. Для сайта с результатами,
на разделы которого ссылаются, это нарушает стабильность постоянных ссылок.

**Решение.** Разделам, на которые есть ссылки, заданы явные латинские id:
`## Работа без CDN { #cdn }`, `{ #known-hosts }`, `{ #e1 }`… Предупреждение
из текста ошибки — штатная работа `--strict`. Ссылки на эту страницу были
написаны раньше самой страницы, и сборка не прошла, пока якорей не
появилось.

## 8. Сбой rsync не останавливал выкладку { #e8 }

**Текст ошибки.** Сообщения об ошибке не было, в этом и проблема. Первая версия
`scripts/helios.sh` фильтровала статистику rsync так:

```bash
rsync … "$site/" "$dest:$upload/" | grep -E '^(Number of …)' || true
```

**Гипотеза.** При `set -o pipefail` код конвейера ненулевой, если упал rsync,
но `|| true` превращает его в успех. Скрипт шёл дальше к `finalize`, а та
проверяет только наличие `index.html`. После частичной загрузки в
`.partial` он мог уже быть, и полурелиз стал бы активным.

**Проверка.** Подставлен `rsync`, который печатает
`rsync: connection unexpectedly closed (0 bytes received so far) [sender]`
и завершается с кодом 23. После исправления выкладка завершается с кодом 23,
сайт остаётся на прежнем релизе `gggg777`, каталог `….partial` остаётся до
следующей выкладки.

**Решение.** Вывод rsync пишется во временный файл, `grep` работает с файлом
отдельной командой, и ошибка rsync через `set -e` останавливает скрипт. Общее
правило: `|| true` в конвейере глушит ошибку любой его команды, а не только
последней.

## 9. `ruff format --check` падает на страницах отчёта { #e9 }

**Текст ошибки** (та же команда, что в workflow `CI`):

```text
$ ruff format --check .
unformatted: File would be reformatted
  --> docs/report/pipelines.md:46:4
   - --8<-- "scripts/check_offline.py"
46 + --8 < --"scripts/check_offline.py"
2 files would be reformatted, 26 files already formatted
```

**Гипотеза.** Свежие версии ruff (0.16) форматируют не только `.py`, но и
блоки ` ```python ` внутри Markdown. Строка вставки `pymdownx.snippets` для
ruff — выражение Python, и он «исправляет» её до неработающего вида.

**Проверка.** Вторая претензия — к примеру кода в [ошибке 7](#e7): ruff
переносит закрывающую скобку. Обе претензии относятся к `docs/`, в файлах
`.py` ошибок нет. Workflow `CI` из первой работы на этом коммите упал бы,
хотя код пакета не менялся.

**Решение.** В `pyproject.toml` добавлено `extend-exclude = ["docs"]`:
ruff проверяет код, а не текст отчёта. Проверено: `ruff check .` и
`ruff format --check .` проходят.

## 10. Helios сбрасывает SSH-соединение до обмена ключами { #e10 }

**Текст ошибки** (и `ssh`, и `ssh-keyscan` с рабочей машины):

```text
$ ssh -v -p 2222 s566109@helios.cs.ifmo.ru
debug1: Connecting to helios.cs.ifmo.ru [77.234.196.4] port 2222.
debug1: Connection established.
debug1: Local version string SSH-2.0-OpenSSH_10.5
kex_exchange_identification: read: Connection reset by peer
Connection reset by 77.234.196.4 port 2222
```

**Гипотеза.** TCP-соединение устанавливается, но сервер обрывает его ещё до
SSH-баннера, то есть до проверки ключей и паролей. Значит, дело не в ключе
или логине, а в фильтре по адресу клиента. Рабочая машина выходит в интернет
через адрес в США (по ipinfo.io). Вероятно, Helios не принимает SSH с
зарубежных адресов.

**Проверка.** С другого компьютера, с российского адреса и без VPN, та же
команда `ssh s566109@helios.cs.ifmo.ru -p 2222` пускает: приглашение к паролю
и баннер `FreeBSD 14.5-STABLE`. Веб `https://se.ifmo.ru/~s566109/` с
американского адреса при этом открывается: фильтр стоит только на SSH.

**Решение.** Главное следствие касается не рабочей машины, а CI:
GitHub-hosted runners работают в зарубежных дата-центрах, поэтому job
выкладки на них получили бы ту же ошибку при любых ключах. Три job, которые
ходят на Helios по SSH, переведены на self-hosted runner с российским IP
(`runs-on: [self-hosted, helios]`). Сборка и Pages остались на GitHub-hosted.
Риски такого runner разобраны в [T4](t4-security.md#self-hosted). Ключ хоста
по той же причине получен не через `ssh-keyscan`, а из SSH-сессии
([T4](t4-security.md#known-hosts)).

## 11. `403 Forbidden` на домашней странице Helios { #e11 }

**Текст ошибки.**

```text
$ curl -sI https://se.ifmo.ru/~s566109/
HTTP/1.1 403 Forbidden
Server: nginx/1.30.4
Content-Type: text/html; charset=iso-8859-1
```

**Гипотеза.** Аккаунт существует (для чужого логина `~s566108` ответ 404, а
не 403), но веб-серверу нечего или нельзя отдать. Либо нет каталога
`~/public_html`, либо у веб-сервера нет права прохода (`o+x`) по домашнему
каталогу.

**Проверка.** На Helios `ls -ld ~ ~/public_html` после создания каталога:
`drwxr-xr-x … /home/studs/s566109` и `drwxr-xr-x … public_html`. До этого
каталога `public_html` не было.

**Решение.** `mkdir -p ~/public_html && chmod 755 ~/public_html && chmod o+x ~`
и тестовый `index.html`. После этого `https://se.ifmo.ru/~s566109/` отдаёт 200.
Скрипт выкладки и так выставляет нужные права на каталоги релизов
([P4](p4-helios.md#setup)). Но создать сам `public_html` и открыть проход по
`$HOME` нужно один раз вручную.

## 12. `install -d -m 700` не работает на Windows-runner { #e12 }

**Текст ошибки** (проверка `scripts/ci-ssh-key.sh` в Git Bash, на такой же
машине, как будущий runner):

```text
install: cannot change permissions of '/tmp/tmp.FcHNLueHAZ/rt/helios-ssh': Permission denied
```

**Гипотеза.** Подготовку SSH писали для Ubuntu-runner. На NTFS права POSIX
эмулируются, и `install -m 700` не может выставить режим каталога. Шаг упал бы
до выкладки на первом же запуске на self-hosted runner.

**Проверка.** Тот же скрипт с `mkdir -p` и `chmod 700 … || true` проходит:
пути из `RUNNER_TEMP` вида `C:\…` переводятся в `/c/…` (`cygpath -u`), CRLF из
секрета удаляются, `ssh -G` видит оба файла, `cleanup` всё удаляет.

**Решение.** Каталог создаётся через `mkdir`, а неудачный `chmod` на Windows
не считается ошибкой. Там доступ к каталогу определяет ACL профиля
пользователя runner. Права на сам файл ключа по-прежнему выставляются, и на
Linux `chmod` выполняется как обычно.

## 13. Выкладка прошла, а job завершился с ошибкой { #e13 }

**Текст ошибки.** Первый запуск `deploy-helios` на self-hosted runner
([запуск](https://github.com/bpa9008-prog/research-graph/actions/runs/38151860177))
помечен как failure. При этом все шаги, включая выкладку (3 с) и healthcheck
(4 с), прошли успешно, а отменён только последний служебный шаг:

```text
Post Run actions/checkout@34e1148…   cancelled
```

**Гипотеза.** Шаги `Post` выполняются после основных, это уборка рабочего
каталога. Статус cancelled означает, что runner прервали. По времени job
закончился в 15:47:21 UTC, а в консоли runner'а `Listening for Jobs` появилось
в 15:48:04. Значит, runner перезапускался.

**Проверка.** Перед перезапуском в консоли Git Bash нажали `Ctrl+C`, чтобы
скопировать вывод. В mintty `Ctrl+C` не копирует, а посылает процессу SIGINT,
и runner остановился посреди шага `Post`. При этом сайт на Helios уже был
обновлён: внешний healthcheck показывает новый хеш коммита.

**Решение.** Повторный запуск job (*Re-run failed jobs*), окно runner'а при этом
не трогали. Копировать текст в mintty нужно выделением мышью (оно копируется
автоматически) или через `Ctrl+Insert`. Вывод для отчёта: статус job и
состояние сайта могут расходиться в обе стороны, поэтому результат выкладки
подтверждает healthcheck, а не цвет значка в Actions.

## 14. Сводка ручного отката свёрстана как список { #e14 }

**Текст ошибки.** В сводке запуска
[#4](https://github.com/bpa9008-prog/research-graph/actions/runs/38153869340)
(ручной откат) активный релиз превратился в пункт маркированного списка, а
заголовок «История» и все строки истории оказались внутри этого пункта, с
отступом. Пометки `*` у активного релиза при этом не видно.

**Гипотеза.** `helios.sh list` помечает активный релиз строкой `* <id>`. Шаг
дописывает этот вывод в `$GITHUB_STEP_SUMMARY`, который GitHub читает как
Markdown. Для Markdown `* ` в начале строки — пункт списка, а следующие строки
без пустой строки между ними — продолжение этого пункта.

**Проверка.** На скриншоте ([P4](p4-helios.md#ci-runs)) строки релизов до
активного выведены обычным текстом, на `20261011T154713Z-d8094bf-r1` вместо
`*` стоит маркер списка, и с него начинается отступ до конца сводки. Это
совпадает с правилами Markdown.

**Решение.** В workflow вывод `list` для сводки заключён в блок
` ```text `. Сам формат вывода не менялся: в консоли и в логе пометка `*`
удобна. Общее правило: в `$GITHUB_STEP_SUMMARY` писать либо Markdown, либо
текст в блоке кода.

## Предотвращено до запуска CI

Найдено при чтении конфигурации; воспроизвести можно командой
`pre-commit run --all-files`.

| Что сломалось бы | Почему | Что сделано |
|---|---|---|
| Хук `check-added-large-files --maxkb=500` | `tex-svg.js` весит 2 059 КБ | `exclude: ^docs/assets/vendor/` в `.pre-commit-config.yaml` |
| Хуки `trailing-whitespace`, `end-of-file-fixer` | изменили бы минифицированный сторонний файл, и его хеш перестал бы совпадать с оригиналом | тот же `exclude` |
