Ниже — шаги из раздела «Ход работы» задания в том порядке, в каком они
выполнялись, с командами и принятыми решениями. Места, которые заполняются

## 1. Python, pip, виртуальное окружение

```bash
python3 --version          # Python 3.12 (CI) / 3.13 (локально)
python3 -m pip --version
python3 -m venv .venv-docs
source .venv-docs/bin/activate   # Windows: .venv-docs\Scripts\activate
```

Для сайта используется отдельное окружение, а не окружение пакета
`research_graph`: сборке сайта не нужны pydantic и typer, а пакету — MkDocs.
Так обновление темы не задевает `uv.lock` основного проекта.

## 2. Зависимости с точными версиями

Зафиксированы в [`requirements-docs.txt`](https://github.com/bpa9008-prog/research-graph/blob/master/requirements-docs.txt):
не только `mkdocs==1.6.1` и `mkdocs-material==9.7.7`, но и все 29 транзитивных
зависимостей. Список нужен целиком: если зафиксировать только верхний уровень,
новая версия `pymdown-extensions` или `markdown` на чистом раннере может
изменить вывод или сломать сборку.

```bash
pip install -r requirements-docs.txt
```

!!! note "Почему не группа `docs` в uv"
    Естественный вариант — `uv add --group docs mkdocs mkdocs-material`, тогда
    версии попали бы в существующий `uv.lock` вместе с хешами. Это не удалось
    сделать в среде подготовки: у неё не было доступа к PyPI (см.
    [Отладка, ошибка 5](debugging.md#e5)). Переход на uv — одна команда при
    наличии сети; workflow для этого меняется в одном шаге установки.

Фиксация версий важна ещё по одной причине: при сборке Material 9.7 печатает
предупреждение команды разработчиков о том, что MkDocs 2.0 будет несовместим с
плагинами и переопределениями тем. Без точной версии `mkdocs` такой релиз мог бы
прийти на раннер сам и сломать сайт.

## 4. Каркас сайта

```text
mkdocs.yml                 конфигурация сайта
mkdocs-cdn.yml             контрольный вариант с CDN (только для эксперимента T4)
docs/                      страницы отчёта
docs/assets/vendor/mathjax MathJax 3.2.2, размещённый локально
overrides/                 частичное переопределение темы (без форка)
scripts/                   выкладка, healthcheck, проверки
```

Тема переопределена через `custom_dir: overrides`, без копирования темы:

- `main.html` добавляет `<meta name="rg-build">` с хешем коммита — контрольную
  строку для healthcheck;
- `partials/copyright.html` выводит в подвале лицензии и метку сборки;
- `partials/source.html` убирает запрос статистики к `api.github.com`
  (подробнее — в [T4](t4-security.md#cdn)).

## 5. Локальная сборка

```bash
mkdocs serve                 # предпросмотр на http://127.0.0.1:8000
mkdocs build --strict        # то же, что в CI
```

## 6. Репозиторий и GitHub Actions

Сайт добавлен в существующий репозиторий проекта, рядом с workflow `CI`
(линтеры и тесты пакета). Новый workflow — `Site`, его полный текст с
комментариями приведён на странице [Тексты пайплайнов](pipelines.md).

В настройках репозитория: **Settings → Pages → Source = GitHub Actions**.

### Два способа публикации на GitHub Pages

| | Push в `gh-pages` (`peaceiris/actions-gh-pages`) | `upload-pages-artifact` + `deploy-pages` |
|---|---|---|
| Что публикуется | содержимое ветки `gh-pages` | артефакт конкретного запуска |
| Нужные права | `contents: write` на весь репозиторий | `pages: write`, `id-token: write` |
| История версий | коммиты в ветке, растёт объём репозитория | список deployment в окружении `github-pages` |
| Откат | `git revert` в ветке `gh-pages` | повторный запуск старого workflow |
| Кто может опубликовать | любой с правом записи в ветку | только job с доступом к окружению `github-pages` |
| Сторонний код в цепочке | сторонний action с правом записи в репозиторий | только actions GitHub |

Выбран второй способ: у job публикации нет права записи в код, нет долгоживущих
секретов, а окружение `github-pages` по умолчанию разрешает выкладку только с
основной ветки. Подробный разбор прав — в [T4](t4-security.md).

## 8. Workflow под площадку развёртывания

Workflow собирает сайт дважды — для GitHub Pages и для Helios — и публикует
каждую сборку своим способом. Отличаются только адрес (`SITE_URL`) и метка
площадки (`BUILD_TARGET`); исходники и версии пакетов одни и те же.

## 9. Базовый URL

| Площадка | `site_url` | Где лежит сайт |
|---|---|---|
| GitHub Pages | `https://bpa9008-prog.github.io/research-graph/` | подкаталог `/research-graph/` |
| Helios, основная ветка | `HELIOS_BASE_URL`, например `https://⟨хост⟩/~sXXXXXX/rg/` | подкаталог `~sXXXXXX/rg/` |
| Helios, ветка `feature/x` | `HELIOS_BASE_URL` + `preview/feature-x/` | вложенный подкаталог |

`site_url` в `mkdocs.yml` читается из переменной окружения:
`site_url: !ENV [SITE_URL, "https://bpa9008-prog.github.io/research-graph/"]`.

Что ломается при неправильном `site_url` в подкаталоге:

- **страница 404**. На остальных страницах пути относительные
  (`assets/...`), а в `404.html` — от корня хоста, взятые из пути `site_url`,
  потому что этот файл отдаётся по любому адресу. Проверено: при
  `SITE_URL=https://example.org/~s000000/rg/` в `404.html` стоит
  `href="/~s000000/rg/assets/stylesheets/main…css"`. Со значением для GitHub
  Pages на Helios страница 404 будет искать стили в `/research-graph/assets/`
  и останется без оформления. Чтобы Apache вообще отдавал эту страницу, нужен
  `.htaccess` с `ErrorDocument 404 /~sXXXXXX/rg/404.html`;
- **`sitemap.xml` и `<link rel="canonical">`** указывают на другую площадку —
  поисковики считают Helios копией;
- **ссылки вида `/assets/...`** в Markdown или переопределениях темы ведут в
  корень хоста, а не сайта. Такие ссылки ловит `validation.absolute_links`.

`use_directory_urls: true` (по умолчанию) даёт адреса вида `report/t4-security/`.
Это работает и на Pages, и на Apache Helios, потому что оба отдают `index.html`
для каталога. При открытии сайта как файлов (`file://`) нужно `false`.

## 10. Проверка результата

Проверка выполняется скриптом `scripts/healthcheck.sh` после каждой выкладки,
а не на глаз:

| Проверка | Как |
|---|---|
| Код ответа | главная — 200, несуществующий адрес — 404 |
| Контрольная строка | `<meta name="rg-build" content="<хеш коммита>">` совпадает с хешем запуска |
| Поиск | `search/search_index.json` отдаётся и является JSON с записями |
| Формулы без CDN | `assets/vendor/mathjax/tex-svg.js` отдаётся с самого сайта, страница с формулами — 200 |
| Нет внешних ресурсов | `scripts/check_offline.py` на этапе сборки |

Отображение формул при недоступных CDN проверено в браузере — см.
[T4 → Работа без CDN](t4-security.md#cdn).
